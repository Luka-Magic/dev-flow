# board: dev-flow の進み具合を 1 画面で見るアプリ(仕様)

2026-11-28。計画の質問票 `devflow-board`(ラウンド 1〜5)で決めた内容を、言葉でまとめたもの。
モックは使い捨てで、正はこの文書に置く。

## 目的

並列運用では、子セッションが 1 つ進むたびに長い報告が中心セッションのチャットに届く。
進み具合・URL・指示を 1 枚の表に移し、チャットを遡らずに「次にやること」へ行けるようにする。

- 全プロジェクトを 1 つのアプリで見る。
- 質問票への回答、PR 案と issue 案の承認、子への短い指示が、この画面で済む。
- Claude Code の利用枠(5 時間・週)と、セッションごとのコンテキスト使用率も出す。

1 人用。ログインなし。127.0.0.1 で待ち受け、外からは Tailscale の中継だけで開く。

## 用語

- **題材**: 表の 1 行。issue 1 つ、または issue のない作業 1 つ(小さな変更、issue を作る前の計画、PR だけ出すもの)。
- **段階**: 計画 / 仕様 / チケット / テストレビュー / UI 確認 / 実装前の説明 / 実装 / レビュー。前後に「未着手」「完了」。
- **記録**: 題材ごとの追記専用のファイル(1 行 1 件の JSON)。子と中心が `flow` コマンドで書く。
- **自分の番**: 人の操作を待っている状態。回答待ちの質問票、未回答の実装前の説明、承認待ちの PR 案・issue 案、確認の選択肢で止まっているセッション。
- **配達係**: 画面からの指示を 1 件届けて終わる、使い捨ての小さなセッション。公式のセッション間メッセージで送る。

## 画面

画面は 1 枚。

1. **上の帯**: 5 時間枠と週の枠の使用率と戻る時刻。表に出ていないセッションのコンテキスト使用率(何分前の値かを添える)。
2. **プロジェクトのタブ**: 自分の番の件数を札で出す。出すプロジェクトは自動(並列運用の設定があるもの、進行中の題材があるもの)。プロジェクトの分からない質問票は「その他」のタブ。
3. **表**(タブごと): 全部の行を出す。上から、完了、番号のない進行中の行、番号のある行(番号順)。
   開いたときは最初の進行中の行が一番上に見える位置から始まり、上へスクロールすると完了に遡る。
   札(進行中・未着手・完了)で絞り込める。
   - 列: 番号 / 題 / 段階(8 つの横棒と名前)/ 自分の番 / セッション(動いている・止まった理由と時間)/ コンテキスト使用率 / 最新の報告(1 行)/ リンク(質問票・issue・PR・プレビューのうち、あるもの)
   - 番号のない行は、番号の欄が空くだけで、ほかは同じ。
   - スマホ幅では 番号・題・段階・自分の番 だけにする。
4. **行を押すと**: 表の上に重なって開く(スマホ幅では画面いっぱい)。
   - 左: 今見るもの(質問票、実装前の説明、PR 案・issue 案の全文)。その下に指示の欄(その題材のセッションに送る文、承認・「直して」のボタン)。
   - 右: 報告の履歴(新しい順、1 行ずつ)。成果物の一覧(段階ごとに、計画の質問票・仕様・承認したルール・モック・PR)。
   - 確認の選択肢で止まっているときは、何の許可を求めているかを出す(画面からは答えない)。

## 情報の流れ

1. **子 → 記録**: 段階が変わったとき・報告したいときに、子が `flow` コマンドで記録する。
2. **子 → 中心**: PR 案と「詰まった」だけを、今と同じセッション間メッセージで送る。それ以外は記録だけ。
3. **画面 → 子・中心**: 配達係が宛先のセッションへ直接届ける。中心は中継しない。
   届かないときは tmux への入力に切り替える。確認の選択肢が出ている窓には送らない。
   画面から送った文は、その題材の記録に残す(中心は記録を読めば分かる)。

PR 案・issue 案は記録の中に決まった形で書く。画面で「承認」を押すと、中心へ「承認された」と届き、中心が GitHub に作る。
PR を作る前の検査(`check-pr.sh`)は今の分担のまま中心が行う。

## 画面が読むもの

| 情報 | 出所 |
|---|---|
| 段階、報告、PR 案・issue 案、送った指示 | 記録 |
| 質問票の状態と URL | grill-visual の `/api/state` |
| issue と PR の一覧、CI | `gh`(結果を短時間キャッシュ)。GitHub を使わないプロジェクトは記録と質問票だけで行を作る |
| セッションの状態、止まった理由と時間 | Claude Code のセッション一覧と、tmux の窓の表示 |
| コンテキスト使用率、利用枠 | ステータス行のスクリプトが、セッションごとに書き出すファイル |

段階は記録を正とする。質問票や PR の有無から導ける段階と食い違うときは、行に印を出す。

## テストが叩く入口(seam)

2 つ。どちらも、記録・質問票の状態・`gh` の出力・セッション一覧を入れた一時フォルダを相手に動かす。

1. **HTTP**: `GET /api/board`(全プロジェクトの表を 1 つの JSON で返す)、`POST /api/send`(指示を送る。配達は差し替え可能な部品で、テストでは偽物を使う)、`POST /api/approve`(PR 案・issue 案の承認)。
2. **CLI**: `flow step|report|stuck|pr-draft|issue-draft`(記録に 1 件足す)。

画面(HTML)は `/api/board` を描くだけにし、判定は持たせない。

## 作り

- 置き場所: このリポジトリの `board/`。Python の標準ライブラリだけで動かす(grill-visual と同じ流儀)。画面は 1 ファイル。
- 記録の置き場所と、プロジェクト名・ホスト名などの個人の設定は、リポジトリの外に置く。
- 質問票は grill-visual の仕組みのまま。board が同じ入口の下で中継し、行を押したところに埋め込む。
- URL: 作っている間は別のポートで動かす。使えると確かめたら、今の質問票の入口(統合ページ)を board に入れ替える。今の形の質問票の URL(`<root>#<topic>`)はそのまま開ける。

## 最初の版に入れないもの

画面からの子の起動 / マージと片付けの指示 / 確認の選択肢への回答 / スマホへの通知 / issue 案の編集。

## 進め方

- UI モック: 2 段階(計画で粗い案は見た。実装の直前に、本物の部品で組んだモックをもう一度見る)。
- テストレビュー: 軽(ルールの一覧をチャットで確認し、凍結しない)。
- 最初に確かめること: 配達係で実際に届くか(止まっている相手が起きるか、相手の権限の設定で保留されないか)。届かなければ tmux を本線にする。

## チケットの案(縦切り)

1. 表が出る: 1 プロジェクト分の issue・質問票・セッションの状態を `/api/board` と画面に出す。
2. 記録: `flow` コマンドと、段階・最新の報告・食い違いの印。
3. 全プロジェクト: タブ、自分の番の札、番号のない行、「その他」。
4. 行を押す: 重ねて開く枠、質問票の埋め込みと回答、報告の履歴、成果物の一覧。
5. 使用量: ステータス行からの書き出しと、上の帯・コンテキストの列。
6. PR 案・issue 案: 決まった形、全文の表示、承認と「直して」。
7. 指示: 配達係の試験、送信、tmux への切り替え、記録への残し方。
8. スキルの文面: 子の報告を記録に移す(dev-flow と並列運用の指示文、プロジェクトごとの子の定義)。
9. 入口の入れ替え: 質問票の入口を board にする。
