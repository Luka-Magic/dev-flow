# 実装前の説明(ステップ 6)

計画・仕様・テストレビュー・UI 確認で決めたことを、実装に入る前に 1 枚の文書で「こうします」と説明し、最後にユーザーの OK をもらう。
決めたことの食い違いを、実装の前に潰すためである。どの深さでも行う。

## 作り方

- html スキルの規範で書く。
- 保存先は `~/.agent/diagrams/{yyyymmdd}-plan-<チケットslug>.html`。grill-visual と同じサーバーで配信され、`./design-system/` を共有する。URL は質問票と同じホスト名で出す。

## 中身(この順)

深さが両方 `none` の小さな変更なら、各項目は数行ずつでよい。

1. 何を作るか・作らないか(spec の要点)
2. 完了条件。深さが `full` なら承認済みルールの一覧(文で書き、ID は括弧で添える)。`light` ならチャットで OK をもらったルール。`none` なら spec から言える完了条件。
3. 画面。ui-check で承認したモックへのリンクと、変わる点。UI の深さが `none` なら、変わる部品と振る舞いを文で書く。
4. 進め方。チケットの順、触るファイルの範囲、テストの seam。
5. 決めていないこと、後回しにしたこと(あれば)。

## 「これで良いか」の回答欄

- 文書の末尾に `dev-flow/assets/confirm-form.html` の回答欄を貼る。`data-topic="plan-<チケットslug>"`、`data-round` は 1 から。
- 選択肢は「このまま進める / 直す(メモ必須)」。
- 回答は `~/.agent/diagrams/answers/plan-<slug>-round-<N>.json` に届く。grill-visual と同じく出現を待つ。`answers.confirm` が `["ok"]` か `["fix"]`、メモは `notes.confirm` に入る。

## 「直す」が来たら

- 中身に応じて戻る先を決める。作るものや完了条件の変更なら test-review の再承認、画面なら ui-check。
- 直したら文書を更新し、`data-round` を 1 つ上げて同じ URL で出し直す。

## 文書の位置づけ

説明文書は記録である。実装の正は従来どおり spec と承認済みのルール・例に置き、文書を実装中に書き換えない。
