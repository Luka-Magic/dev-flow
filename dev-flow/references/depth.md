# 深さを決める(計画のラウンド 1)

小さな変更(チェックボックスをトグルにする、など)にまで、モック 2 段階とテストの承認をかけない。
そのために、UI モックとテストレビューの 2 軸で「深さ」を選ぶ。
計画の grill のラウンド 1 の先頭 2 問で聞き、AI が題材を見て推奨を付け、`why` に理由を 1 行で書く。
ユーザーの回答が正である。子セッションが自分の判断で軽くすることはしない。

## 2 問と、選択肢ごとのフロー

| 問い(`id`) | 選択肢 `key` | その後のフロー |
|---|---|---|
| UI モック(`depth-ui`) | `none` なし | モックも ui-check も作らない。実装後のスクリーンショットを PR に添える |
| | `detail` 詳細だけ | 計画ではモックを出さず(文字のブレッドボードまで)、ui-check の一時ルートだけ作る |
| | `full` 2段階 | 計画で粗い静的モック(複数案)を出し、ui-check で一時ルートを作る |
| テストレビュー(`depth-test`) | `none` なし | test-review をしない。テストは TDD で書く。凍結しない。レビューでテストの diff を見る |
| | `light` 軽 | ルール一覧(ルール文と主な例)をチャットに出し、ユーザーの OK で実装へ。凍結しない |
| | `full` フル | test-review スキルを実行する(質問票で承認し、`docs/test-cases/` に凍結する) |

`id` と `key` はこの表から変えない。並列運用の `check-pr.sh` が回答ファイル(`answers/` の `depth-ui`)を読んで ui-check の要否を判定するためである。issue のラベルや本文には書かない。

## 推奨の目安

UI モック:

- UI に触れない → `none`
- 部品の差し替え・文言・並び順だけ → `none`
- 既存の画面に状態や項目が増える → `detail`
- 新しい画面、または画面の構造が変わる → `full`

テストレビュー:

- 分岐やデータの扱いが変わらない → `none`
- 分岐が少しある → `light`
- データを消す・お金・権限・外部連携・分岐が多い → `full`

## ラウンドの組み方

- **ラウンド 1** = 深さの 2 問 + 深さに関係なく聞ける計画の問い。深さが両方 `none` でも決めることはある(どの画面のどの項目か、既存データの扱い、既定値、例外時の振る舞い、など)。それらは深さの回答を待たずに最初から並べる。
- **ラウンド 2 以降**は、前のラウンドの回答を受けて作る。中身は 2 種類で、どちらも同じラウンドに並べる。
  1. 回答から出た掘り下げと新しい論点。メモや自由記述で出た疑問、選んだ案で新たに決めること、など。モックやテストに関係なくても聞く。
  2. 深さの答えで要否が決まる問い。モックの案を比べる問い、テストのリスクの切り分け、など。
- 深さが両方 `none` で、ラウンド 1 の回答で決めることが尽きたら、計画の grill はラウンド 1 で終えてよい。仕様化とチケット分割も題材の大きさなりに短くする(issue 1 本、spec は数行でよい)。

## 途中で選び直す

題材が膨らんだら(例: 「部品の差し替え」のはずが画面の構造に触れた)、止めて、計画の grill に深さを選び直す問いを出す。
選び直しは新しいラウンドで、同じ `id` で聞く。最新の回答が正になる。
