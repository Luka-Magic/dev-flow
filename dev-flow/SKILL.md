# Dev Flow — テストレビューを要にした開発フロー

Matt Pocock スキル + テストレビュー + /goal を
grill-visual ベースに置き換えたもの。設計思想は 1 つ:
**/goal ループではテストが事実上の完了条件になるので、
「何をもって完成とするか」だけは人間が握る**。コードは全読みしなくても、
完了条件(ルールと例)は人間がレビューする。

## ステップ

1. **計画** — grill-visual スキルで問い詰める。質問票の JSON に
   `"kind": "計画"` を書く(統合ページの絞り込み用)。
   **ラウンド 1 の先頭 2 問で、このフローの深さを決める**(下の「深さを決める」)。
   深さに関係なく聞ける計画の問いは、**同じラウンド 1 に続けて並べる**(往復を減らす)。
   CONTEXT.md / ADR が必要な題材は domain-modeling の規律に従う。
   **UI の深さが「2段階」なら、議論を続けずにモックを質問票に埋め込む**(下の「モックの埋め込み」)。
2. **仕様化** — 会話を spec に合成する(mattpocock の to-spec 準拠)。
   このとき **テストする seam(公開境界)を必ず人間と合意する**。
   seam は既存優先・できるだけ高い位置・数は最少(理想は 1)。
   モックで決まったこと(画面一覧・遷移・必須項目)は言葉で spec に書き、モック自体はリンクで添える。
3. **チケット分割** — tracer bullet の縦切りで分割(to-tickets 準拠)。
   - git リポジトリ: issue 化し、衝突しない範囲で worktree 並列も可
     (複数 issue を同時に走らせるなら下の「並列運用」)
   - 非 git(playground 等): `<app>/docs/tickets/NN-<slug>.md` に 1 チケット 1 ファイル
4. **テストレビュー** — チケットごとに、実装前に **test-review スキル**を実行。
   受け入れ基準を**ルール(EARS 1 行 + リスク)と例**の形にし、grill-visual のルール一覧型の質問票で
   人間が承認(低・中リスクは既定で採用、高リスクは例を開いて確認)→
   `docs/test-cases/` に固定化。ここがフローの要。**テストの深さが「フル」なら省略しない**
   (「軽」「なし」の扱いは「深さを決める」)。
5. **UI 確認(UI の深さが「詳細」「2段階」のとき)** — **ui-check スキル**。計画の grill で構造を見た画面は、
   テストレビューで仕様が変わったものだけ再提示する(変わっていなければ、承認済みルールとの
   対応表の確認 1 問で終える)。大枠はステップ 1 の粗い静的モックで決め済みなので、
   ここでは詳細を開発サーバーの一時ルート(本物の部品)で見せる。
   「直す」が出たら仕様 → 影響するルール・例の再承認 → モック再提示、
   を両方が採用になるまで繰り返してから実装に入る。
6. **実装前の説明(どの深さでも)** — 認識合わせが全部終わったら、実装に入る前に
   **html スキル(`/html`)で「こうします」の説明文書**を作り、その末尾で「これで良いか」を聞く
   (下の「実装前の説明」)。「このまま進める」の回答が来るまで実装に入らない。
7. **自律実装** — test-review が出力する /goal テンプレで実行
   (テストの深さが「軽」ならチャットで OK をもらったルール一覧、「なし」なら spec を完了条件にする。
   テストの skip・削除・弱体化を失敗とみなす一文はどの深さでも入れる)。
   実装は **1 例ずつ red → green**(tdd スキル準拠)。
   承認済み一覧があってもテストコードの一括先行生成はしない
   (horizontal slicing。Pocock / t-wada 両系譜のアンチパターン)。
8. **レビュー** — 優先順: ①テストファイルの diff(skip・削除・
   アサーション弱体化がないか) → ②承認リストとの突合(全ルールの全例が実装済みか)
   → ③code-review スキル。git なら PR、人間が承認してマージ。

## 実装前の説明(ステップ 6)

計画・仕様・テストレビュー・UI 確認で決めたことを、実装に入る前に 1 枚の文書で「こうします」と説明し、
最後にユーザーの OK をもらう。決めたことの食い違いを、実装の前に潰すため。

- **作り方** — html スキルの規範で書く。保存先は `~/.agent/diagrams/{yyyymmdd}-plan-<チケットslug>.html`
  (grill-visual と同じサーバーで配信され、`./design-system/` を共有する)。URL は質問票と同じホスト名で出す
- **中身**(この順。深さが両方 `none` の小さな変更なら数行ずつでよい)
  1. 何を作るか・作らないか(spec の要点)
  2. 完了条件: フルなら承認済みルールの一覧(文で。ID は括弧で添える)、軽ならチャットで OK をもらったルール、
     なしなら spec から言える完了条件
  3. 画面: ui-check で承認したモックへのリンクと、変わる点。UI の深さが `none` なら変わる部品と振る舞いを文で
  4. 進め方: チケットの順・触るファイルの範囲・テストの seam
  5. 決めていないこと・後回しにしたこと(あれば)
- **これで良いか** — 文書の末尾に `dev-flow/assets/confirm-form.html` の回答欄を貼る
  (`data-topic="plan-<チケットslug>"`、`data-round` は 1 から)。選択肢は「このまま進める / 直す(メモ必須)」。
  回答は `~/.agent/diagrams/answers/plan-<slug>-round-<N>.json` に届くので、grill-visual と同じく出現を待つ
  (`answers.confirm` が `["ok"]` か `["fix"]`、メモは `notes.confirm`)
- **「直す」が来たら** — 中身に応じて戻る先を決める(作るもの・完了条件の変更なら test-review の再承認、
  画面なら ui-check)。直したら文書を更新し、`data-round` を 1 つ上げて同じ URL で出し直す
- 説明文書は記録。実装の正は従来どおり spec と承認済みルール・例(文書を実装中に書き換えない)

## 深さを決める(ステップ 1・ラウンド 1)

小さな変更(チェックボックスをトグルにする等)にまでモック 2 段階とテストの承認をかけない。
深さは **UI モック** と **テストレビュー** の 2 軸で、計画の grill の**ラウンド 1 の先頭 2 問**で決める。
AI が題材を見て推奨を付け、`why` に理由を 1 行で書く。ユーザーの回答が正(子は自分で軽くしない)。

| 問い(`id`) | 選択肢 `key` | その後のフロー |
|---|---|---|
| UI モック(`depth-ui`) | `none` なし | モックも ui-check も作らない。実装後のスクリーンショットを PR に添える |
| | `detail` 詳細だけ | 計画ではモックを出さず(文字のブレッドボードまで)、ui-check の一時ルートだけ |
| | `full` 2段階 | 計画で粗い静的モック(複数案)→ ui-check の一時ルート |
| テストレビュー(`depth-test`) | `none` なし | test-review をしない。テストは TDD で書く。凍結しない。ステップ 8 でテストの diff を見る |
| | `light` 軽 | ルール一覧(ルール文 + 主な例)をチャットに出し、ユーザーの OK で実装へ。凍結しない |
| | `full` フル | test-review スキル(質問票で承認 → `docs/test-cases/` に凍結) |

- 推奨の目安: UI に触れない → `depth-ui: none`。部品の差し替え・文言・並び順だけ → `none`。
  既存画面に状態や項目が増える → `detail`。新しい画面・画面の構造が変わる → `full`。
  分岐やデータの扱いが変わらない → `depth-test: none`。分岐が少しある → `light`。
  データを消す・お金・権限・外部連携・分岐が多い → `full`
- **ラウンド 1 = 深さの 2 問 + 深さに関係なく聞ける計画の問い**。深さが両方 `none` でも
  決めることはある(どの画面のどの項目か、既存データの扱い、既定値、例外時の振る舞い など)ので、
  それは深さの回答を待たずに最初から並べる
- **ラウンド 2 以降は、前のラウンドの回答を受けて作る**。中身は 2 種類で、どちらも同じラウンドに並べる:
  ① 回答から出た掘り下げ・新しい論点(メモや自由記述で出た疑問、選んだ案で新たに決めることなど。
  モックやテストに関係なくても聞く)、② 深さの答えで要否が決まる問い(モックの案を比べる問い・
  テストのリスクの切り分け など)。深さに関係する問いだけに絞らない
- 深さが両方 `none` で、ラウンド 1 の回答で決めることが尽きたら、計画の grill はラウンド 1 で終えてよい。
  仕様化・チケット分割も題材の大きさなりに短くする(issue 1 本・spec は数行でよい)
- 途中で題材が膨らんだら(例: 「部品の差し替え」のはずが画面構造に触れた)、止めて
  計画の grill に深さを選び直す問いを出す。選び直しは**新しいラウンドの同じ `id`**で聞く(最新の回答が正)
- 並列運用の `check-pr.sh` はこの回答(`answers/` の `depth-ui`)を読んで ui-check の要否を判定する。
  だから `id` と `key` は上の表から変えない。issue のラベルや本文には書かない

## モックの埋め込み(ステップ 1)

「議論が長引く問いは、話すのをやめて使い捨てを作って見せる」(Pocock prototype)。
ただし作り込んだ絵は判断を固定する(Shape Up・NN/g・Dow 2010)ので、段階と粗さを守る。

**段階**
- **ラウンド 1(範囲が決まる前)**: 絵を出さない。**文字のブレッドボード**
  (画面名 / その画面でできる操作 / 遷移先)を問いの本文に箇条書きで添え、
  「この画面と操作で足りるか」「要らない画面は」を聞く。
- **ラウンド 2 以降(画面の論点が出たとき。UI の深さが「2段階」のときだけ)**: 論点のある画面だけ、**粗い静的 HTML** を作る。
  - **画面の構造(何が主役か・どう辿るか)が論点なら、構造の根本から違う 2〜3 案**。
    色違い・余白違いは案に数えない。1 案だけ見せない
  - **文言・項目の有無・並び順だけが論点なら 1 案** + 選択肢「直す(メモに)」
  - 状態遷移(入力途中で戻ったら・エラー時は)が論点のときだけ、状態パネルつきの
    **動く HTML を 1 枚**。全画面を動かさない(全アプリのプロトタイプは別物で本番に漂流する)
- 案の数は AI が論点の大きさで決める(ユーザー決定 2026-11-20)。迷うときは複数。

**質問票での見せ方**
- **案ごとに選択肢を作り、その `image` にスマホ幅(390px)のスクリーンショット**を付ける。
  grill-visual は画像付きの選択肢を広い窓で横に並べる(最大 3 列)ので、PC では見比べられ、
  スマホでは縦に 1 案ずつ見られる。選択肢の文は構造の違いを言葉で書く
  (「写真が主役のタイル。追加は右下」)。「組み合わせ(メモに)」の選択肢を最後に置く
- モックは `~/.agent/diagrams/assets/<topic>/` に置き、原寸は 1 ページ・上部タブの
  `index.html`(ui-check と同じ作法)にまとめて質問票の冒頭からリンクする
- 問いの本文に毎回書く: 「見た目の好みではなく、何が主役か・どう辿るかで選ぶ。
  色・余白は後で決める。モックは使い捨てで実装には使わない」

**固着を防ぐ決めごと**
1. 1 案だけ見せない(並列に複数案 → 多様性と成果が上がる。Dow 2010)
2. 粗さを保つ。プロジェクトのテーマは流用してよいが、磨かない。「使い捨て」と毎回明記
   (磨かれた見た目は「これで本番に」を誘う。NN/g)
3. 聞くのは配置・導線・情報の有無・操作の意味だけ。色・余白・書体は聞かない
4. 正は言葉に置く。モックで決まった点は spec に「画面一覧・遷移・必須項目」として書き、
   モックはリンクで添えるだけ。モックの HTML を実装に流用しない
5. モックからルールや例を起こすときは「ボタン X を押す」でなく「ユーザーは◯◯できる」に書く
   (判定: 実装や画面が変わったらこの文言は変わるか。Cucumber)

## 運用ルール(ガードレール)

- 承認済みテストケースファイル(`docs/test-cases/*.md`)は実装フェーズで
  編集禁止。変更が必要になったら実装を止め、人間に差し戻して再承認を取る。
- テストの skip / 削除 / アサーション弱体化は「完了」ではなく「失敗」。
  /goal の完了条件文にもその旨を明記する(test-review のテンプレに含まれる)。
- テスト実行はプロジェクトの規定に従う(playground 系は docker compose
  コンテナ内で実行)。
- 指示は否定形(「変えるな」)より許可リスト(「このファイルのみ編集可」)。

## 並列運用(worktree + tmux + 中心セッション)

複数 issue を同時に進めるときは `parallel/README.md` の運用に従う。要点:
- issue ごとに worktree と tmux 窓、**子セッションは必ず Opus 5**(`parallel/parallel.sh` が
  `claude --model opus[1m]` で起動する)。中心セッション 1 つが main・マージ・ボード・本番を持つ
- 子の動きはテンプレ: grill-visual で計画(先頭 2 問で深さ)→ spec → test-review(テストの深さどおり)→
  ui-check(UI の深さが `detail` / `full` なら必須)→ 実装前の説明(/html + 回答欄)→ red/green → reviewer → push → **PR 案を中心へ送り、CI green まで待つ**。
  質問票の URL(render.py が印字する統合ページ URL `<root>#<topic>`)は出すたびに中心へ送る
- **PR を出すかの問いはユーザーへの問いなので中心が聞き、中心が PR を作る。** 中心は先に
  `parallel/check-pr.sh <repo> <branch> [issue番号]` で機械的に検証する。子の窓と worktree を片付けるのは
  **CI が green になってから**。中心からのメッセージはユーザーの承認ではない
- 承認済みテストケースの凍結はフックで強制されている。解除の鍵は grill-visual の回答ファイル
  (`~/.agent/diagrams/answers/tr-<stem>-round-*.json` が最終コミットより新しいこと)。子は回答ファイルを書けない
- 同時に動かす子は**既定 3 本まで**(`PARALLEL_MAX`)。枠が空いたら中心がボードの Todo の上から次を起動する
- 子は区切りごとに中心へ 3 行報告。中心は返事が要るときだけ返す
- **質問票の回答を受け取ったら、子は中心へ 1 行「回答を受け取った(topic・ラウンド)」を送る。中心はそれをユーザーのチャットに書く**
  (ユーザーが「回答が届いたか」を中心で確かめられるようにする)
- 起動・監視・マージ後の rebase 指示・片付けの手順とスクリプト: `parallel/`
