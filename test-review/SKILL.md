# test-review

実装の前に「何をもって完成とするか」をルールと例の形にし、人の承認を得てから凍結する。
承認済みの一覧が、/goal の完了条件と、実装(red → green)の正本になる。

承認の単位は**ルール**である。人は「このルールで完成と言えるか」だけを判断し、例は網羅の確認に目を通すだけでよい。
根拠は Example Mapping(ルール / 例 / 問い)、Gherkin の `Rule`、ISTQB のリスクベーステストにある(`docs/2026-10-17-research-test-review-and-mocks.md`)。

dev-flow の中では、計画の grill で選んだテストの深さ(`depth-test`)が `full` のときに使う。`light` と `none` の扱いは dev-flow の `references/depth.md` にある。単独で「テストレビューして」と頼まれたときは、深さに関係なく実行する。

## 用語

- **ルール**: 1 行の業務ルール。「ユーザーは◯◯できる」「◯◯のときは△△しない」の文。
- **例**: ルールを示す具体的なテストケース。入力と期待結果を持つ。Gherkin の `Examples` 表に相当する。
- **EARS**: ルールに添える 1 行の要件文。`When <きっかけ>, the <system> shall <応答>` の形。
- **リスク**: ルールごとの 高 / 中 / 低。影響 × 不確かさで決める。
- **seam**: テストが叩く公開境界。
- **凍結**: 承認済みの一覧を `docs/test-cases/<slug>.md` に保存し、実装中は編集しないこと。

## 手順

1. **前提を確認する**。対象チケットの受け入れ基準と、合意済みの seam を読む。seam が未合意なら、ルールを書く前に人に確認する。候補を挙げるときは、名前だけでなく「この seam だと何が拾えて何が漏れるか」を添える。
   終わり: seam に人の OK がある。
2. **ルールと例を作る**。まずルールを立て、その下に例をぶら下げる。書き方は [references/rules-and-cases.md](references/rules-and-cases.md)。
   終わり: 全ルールに EARS 行とリスクがあり、例の分類が正常系・異常系・境界値・例外を網羅している。
3. **提示前に自問する**。
   - 各例に: 「実装にバグを 1 つ入れたら、この例は落ちるか」。落ちない例(曖昧な期待値、トートロジー)と論理的な重複を除く。
   - 各ルールに: 「このルールの例を全部通しても、ルールが守られていない実装はあり得るか」。あり得るなら例を足すか、ルールを分ける。
   - 未解決の問い(Example Mapping の赤カード)が残っているなら、質問票の冒頭に書き、そのルールは「仮」と明記する。
4. **質問票でレビューする**。grill-visual のルール一覧型の問いで出す。データの形と見せ方の決めごとは [references/questionnaire.md](references/questionnaire.md)。
   終わり: 全ルールが採用になった。
5. **凍結する**。承認済みの最終形を `<app>/docs/test-cases/<チケットslug>.md` に保存する。形式は [references/frozen-file.md](references/frozen-file.md)。以後、このファイルは実装中に編集しない。変更が要ると分かったら実装を止め、人に差し戻し、再承認を取ってから続ける。
6. **/goal テンプレを提示する**。凍結したパスを埋める。N はチケットの規模で 10〜20 が目安。

   ```
   /goal <path>/docs/test-cases/<slug>.md の全ルールの全例がテストコード化され、
   各テストが一度 red(失敗)を経て green になり、全テストスイートが
   (コンテナ内実行で)パスしている。テストの skip・削除・アサーション
   弱体化・承認リスト外の仕様変更があれば「不可能」と判定する。
   実装は 1 例ずつ red→green で進める。N ターンで停止。
   ```

   実装は tdd スキル準拠で、1 例ずつ進める。テストコードを一括で先に生成しない。

## レビューの観点

質問票の注記(`note`)に書く内容の元になる。

1. バグを入れたら落ちるか(ミューテーション思考)
2. 期待値は具体的で、実装から独立しているか
3. 境界値と異常系が業務的に妥当か
4. 振る舞いの文がそのままテスト名になるか(HOW ではなく WHAT。UI の手順になっていないか)
5. seam 経由か(実装の詳細に触れていないか)
6. リスクの根拠を書いたか(高 = 業務停止・金銭や権限・新しく曖昧)
