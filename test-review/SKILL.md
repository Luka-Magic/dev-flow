# Test Review — 実装前テストケースの人間承認

実装前に「何をもって完成とするか」を自然言語のテストケース一覧にし、
人間の承認を得てから固定化する。承認済み一覧が /goal の完了条件と
実装(red-green)の正本になる。

## 手順

### 1. 前提確認

対象チケット/issue の受け入れ基準と、合意済みの seam(テストする公開境界)を
読む。**seam が未合意ならテストケースを書く前に人間に確認する**(候補を挙げる
ときは名前だけでなく「この seam だと何が拾えて何が漏れるか」を添える)。

### 2. テストケース表を作る

Markdown 表。列: `ID / 振る舞いの説明 / 入力 / 期待結果 / 分類`。

- 分類は **正常系・異常系・境界値(空、0、負数、最大長)・例外** を必ず網羅
  (指定しないとハッピーパスに偏る)
- 期待結果は**具体的な値**。「正しく動く」「エラーにならない」は禁止。
  期待値は独立した正解(仕様・手計算・既知の実例)から取る。実装と同じ
  計算式で導いた値はトートロジーなので禁止
- テストは合意済み seam 経由のみ。内部実装(private 関数、DB 直接参照、
  内部コラボレータのモック)には触れない
- 数合わせの分岐網羅はしない。業務的に意味のあるケースだけ
- 振る舞いの説明は「ユーザーは◯◯できる」形式(テスト名にそのまま使える)

### 3. セルフチェック(提示前)

各ケースに自問: **「実装にバグを 1 つ入れたら、このケースは落ちるか?」**
落ちないケース(曖昧な期待値・トートロジー)と論理的な重複を除去してから出す。

### 4. grill-visual 質問票でレビュー

grill-visual スキルの手順(JSON → render.py → serve.sh → Monitor)に従う。
提示する URL は render.py が印字する統合ページ URL(`<root>#tr-<slug>`)。
topic 名は `tr-<チケットslug>`。JSON に `"kind": "test-review"` を書く(統合ページの絞り込み用)。

- 1 ケース = 1 質問。選択肢: **採用(推奨)/ 修正(メモ欄に内容)/ 削除**
  (件数が多くて関係するケースをまとめるときも、1 問に 5 件まで)
- **記号(A1・U3・R2 などのケース ID)をユーザーに読ませない。** ID は表の管理用。
  質問の題は「ユーザーは◯◯できる」の文で、まとめた場合は各ケースを文で列挙する。
  グループの文字(A = API、U = 画面 …)を使うなら、intro と info タブに凡例を置き、
  質問の題では文字ではなく日本語の分類名(「API・探鳥行を作る」「画面・写真タブ」)で書く。
  ユーザーの声: 「R, N などのアルファベットが分からず、それだけあまり意味をなしてない」
- **各問の本文は、1 ケース = 1 行の横長の表**(ユーザー指定の形)。列は
  「振る舞い / 入力 / 期待結果 / 分類」で、その問いに含まれる数件が縦に並んで一目で比べられること。
  ケースごとに縦の表を作らない。文章で流さない:
  ```html
  <table class="cases">
  <tr><th>振る舞い</th><th>入力</th><th>期待結果</th><th>分類</th></tr>
  <tr><td>ユーザーは◯◯できる</td><td>…</td><td>…具体的な値…</td><td>正常系</td></tr>
  <tr><td>ユーザーは△△できない</td><td>…</td><td>…</td><td>異常系</td></tr>
  </table>
  ```
  ID は表に列を足さず、必要なら振る舞いの末尾に小さく添える。
  ユーザーの声: 「4 つが各 1 行になっていて、振る舞いが 1 列で 4 つ見れたのでパッと見やすかった」
  **この表は test-review の質問票だけ。** 計画の grill や ui-check の質問票には使わない(そちらは従来どおり)。
- `answer_note` に AI 側の注記(なぜこの期待値か、どの境界を突くか)を書く
- info タブに表全体と seam・チケット参照を載せる
- 全体自由記述欄で「足りない観点・ドメイン的な違和感」を明示的に募る
  (ユーザーは推奨どおり選びつつメモ欄で本質的な指摘をする傾向がある。
  メモは必ず反映し、次ラウンドで確認する)
- 修正・追加が出たら該当ケースだけ次ラウンドで再提示。全採用で完了

### 5. 固定化

承認済みの最終表を `<app>/docs/test-cases/<チケットslug>.md` に保存。
ヘッダにチケット参照・seam・承認日を記載。
**以後このファイルは実装フェーズで編集しない**。実装中に変更が必要と
分かったら、実装を止めて人間に差し戻し、再承認を取ってから続ける。

### 6. /goal テンプレを提示

固定化したパスを埋めて提示する(N はチケット規模で 10〜20 目安):

```
/goal <path>/docs/test-cases/<slug>.md の全ケースがテストコード化され、
各テストが一度 red(失敗)を経て green になり、全テストスイートが
(コンテナ内実行で)パスしている。テストの skip・削除・アサーション
弱体化・承認リスト外の仕様変更があれば「不可能」と判定する。
実装は 1 ケースずつ red→green で進める。N ターンで停止。
```

実装は tdd スキル準拠(1 ケースずつ。テストコードの一括先行生成はしない)。

## レビュー観点(質問票に埋める注記の元ネタ)

1. バグを入れたら落ちるか(ミューテーション思考)
2. 期待値は具体的で独立か
3. 境界値・異常系が業務的に妥当か
4. 振る舞いの説明がそのままテスト名になるか(HOW でなく WHAT)
5. seam 経由か(実装詳細に触れていないか)
