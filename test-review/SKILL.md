# Test Review — 実装前テストケースの人間承認

実装前に「何をもって完成とするか」を **ルール(受け入れ基準)と、それを示す例** の形にし、
人間の承認を得てから固定化する。承認済みの一覧が /goal の完了条件と
実装(red-green)の正本になる。

承認の単位は **ルール**。人は「このルールで完成と言えるか」だけを判断し、
例(個々のテストケース)は網羅の確認に目を通すだけでよい。
根拠: Example Mapping(ルール / 例 / 問い)、Gherkin の `Rule`、ISTQB のリスクベーステスト
(`docs/2026-10-17-research-test-review-and-mocks.md`)。

## 手順

### 1. 前提確認

対象チケット/issue の受け入れ基準と、合意済みの seam(テストする公開境界)を
読む。**seam が未合意ならルールを書く前に人間に確認する**(候補を挙げる
ときは名前だけでなく「この seam だと何が拾えて何が漏れるか」を添える)。

### 2. ルールと例を作る

まず **ルール** を立て、その下に **例** をぶら下げる。

**ルール**(1 チケットで 3〜8 件が目安。例の数の 1/3〜1/5):
- 1 行の業務ルール。題は「ユーザーは◯◯できる」「◯◯のときは△△しない」の文
- **EARS 1 行**を添える: `When <きっかけ>, the <system> shall <応答>`
  (Ubiquitous / When / While / If-Then / Where の 5 型。期待値の具体的な値は例の側に置く)
- **リスク**(高 / 中 / 低)を付ける。基準は 影響 × 不確かさ。
  高 = 壊れると業務が止まる・お金や権限に関わる・仕様が新しく曖昧。
  低 = 既存の振る舞いの踏襲・表示だけ・外しても気づいてすぐ直せる
- 画面に関わるルールは、どの画面かを括弧で添える(ui-check の差分確認で使う)

**例**(ルールごとに 1〜5 件。Gherkin の `Examples` 表に相当):
- 列: `ID / 振る舞い / 入力 / 期待結果 / 分類`。ID は `R1-1` のようにルール番号つき
- 分類は **正常系・異常系・境界値(空、0、負数、最大長)・例外** をルール全体で網羅
  (指定しないとハッピーパスに偏る)
- 期待結果は**具体的な値**。「正しく動く」「エラーにならない」は禁止。
  期待値は独立した正解(仕様・手計算・既知の実例)から取る。実装と同じ
  計算式で導いた値はトートロジーなので禁止
- テストは合意済み seam 経由のみ。内部実装(private 関数、DB 直接参照、
  内部コラボレータのモック)には触れない
- 数合わせの分岐網羅はしない。業務的に意味のある例だけ
- 振る舞いは「ユーザーは◯◯できる」形式(テスト名にそのまま使える)。
  **UI の手順(「ボタン X を押す」)で書かない。** 判定は「実装や画面が変わったらこの文言は変わるか」

### 3. セルフチェック(提示前)

- 各例に自問: **「実装にバグを 1 つ入れたら、この例は落ちるか?」**
  落ちない例(曖昧な期待値・トートロジー)と論理的な重複を除去する
- 各ルールに自問: 「このルールの例を全部通しても、ルールが守られていない実装はあり得るか?」
  あり得るなら例を足すか、ルールを分ける
- 未解決の問い(Example Mapping の赤カード)が残っているなら、質問票の冒頭に書き、
  そのルールは「仮」と明記する

### 4. grill-visual 質問票でレビュー

grill-visual スキルの手順(JSON → render.py → serve.sh → Monitor)に従う。
提示する URL は render.py が印字する統合ページ URL(`<root>#tr-<slug>`)。
topic 名は `tr-<チケットslug>`。JSON に `"kind": "test-review"` を書く(統合ページの絞り込み用)。

- 質問は **ルール一覧型**(`"type": "rules"`)。**1 問に 5〜8 ルール**(seam や画面ごとに分ける)。
  各行は 行頭にリスク・ルール文・例の件数(タップで横長表が開く)・右に**採用トグル(既定オン)**・
  💬(押すと行の下に 1 行欄)。末尾に「採用 n / 不採用 n / コメント n」が出る
- **高リスクの行は例を開いた状態で出す。** 中・低は畳んだまま既定で採用(人は開かなくてよい)。
  抜き打ちの明示確認は入れない(ユーザー決定 2026-11-20)
- 質問データの形:
  ```json
  {"id": "Q1", "type": "rules", "title": "API・ログイン(5 ルール・13 例)",
   "body": "seam: HTTP の入口。高リスク 2 件は例を開いて確認してください。",
   "rules": [
     {"id": "R1", "text": "ログインなしでは API を使えない", "risk": "high",
      "ears": "When クッキーなしで API を呼ぶと、システムは 401 を返す",
      "note": "期限切れは 7 日の境界を 8 日で突く",
      "cases": [
        {"id": "R1-1", "behavior": "一覧を見られない", "input": "クッキーなし GET /api/sites",
         "expected": "401", "kind": "異常系"}
      ]}
   ]}
  ```
  回答は `answers["Q1"] = {"R1": "adopt", "R4": "reject"}`、
  1 行コメントは `notes["Q1/R4"]`、問い全体のメモは `notes["Q1"]` に入る
- **記号(R1・R1-2 などの ID)をユーザーに読ませない。** ID は表の管理用。
  行の文は「ユーザーは◯◯できる」の文で、分類や seam は日本語名(「API・ログイン」「画面・写真タブ」)で書く。
  ユーザーの声: 「R, N などのアルファベットが分からず、それだけあまり意味をなしてない」
- 例の表は **1 例 = 1 行の横長の表**(列: 振る舞い / 入力 / 期待結果 / 分類)。
  例ごとに縦の表を作らない。文章で流さない。
  ユーザーの声: 「4 つが各 1 行になっていて、振る舞いが 1 列で 4 つ見れたのでパッと見やすかった」
  **この表は test-review の質問票だけ。** 計画の grill や ui-check の質問票には使わない
- ルールの `note` に AI 側の注記(なぜこの期待値か、どの境界を突くか、なぜこのリスクか)を書く
- info タブにルールと例の全体、seam、チケット参照、未解決の問いを載せる
- 全体自由記述欄で「足りないルール・ドメイン的な違和感」を明示的に募る
  (ユーザーは推奨どおり選びつつメモ欄で本質的な指摘をする傾向がある。
  メモは必ず反映し、次ラウンドで確認する)
- 「不採用」「コメントあり」のルールだけ次ラウンドで再提示(直した例の表を開いた状態で)。
  全採用で完了

### 5. 固定化

承認済みの最終形を `<app>/docs/test-cases/<チケットslug>.md` に保存。
ヘッダにチケット参照・seam・承認日・質問票のラウンドを記載。
形式は **ルール見出し + EARS 行 + 例の表**:

```markdown
# <チケット名> 受け入れテストケース(承認済み)

- チケット: … / 仕様: … / seam: …
- 承認: 2026-11-20(grill `tr-<slug>` R1〜R2。高 2 件は明示採用、低 3 件は既定採用)

> **このファイルは実装フェーズで編集しない。** 変更が必要になったら実装を止めて差し戻し、
> 再承認を取ってから続ける。skip・削除・アサーションの弱体化は「完了」ではなく「失敗」。

## R1 ログインなしでは API を使えない  (リスク 高・採用)
When クッキーなしで API を呼ぶと、システムは 401 を返す

| ID | 振る舞い | 入力 | 期待結果 | 分類 |
|---|---|---|---|---|
| R1-1 | 一覧を見られない | クッキーなし `GET /api/sites` | 401 | 異常系 |

## R2 手元スイッチが入っていればログインなしで使える  (リスク 低・既定採用)
…
```

**以後このファイルは実装フェーズで編集しない**。実装中に変更が必要と
分かったら、実装を止めて人間に差し戻し、再承認を取ってから続ける。
(check-pr.sh と凍結フックはファイル単位で見るので、この形式でそのまま動く)

### 6. /goal テンプレを提示

固定化したパスを埋めて提示する(N はチケット規模で 10〜20 目安):

```
/goal <path>/docs/test-cases/<slug>.md の全ルールの全例がテストコード化され、
各テストが一度 red(失敗)を経て green になり、全テストスイートが
(コンテナ内実行で)パスしている。テストの skip・削除・アサーション
弱体化・承認リスト外の仕様変更があれば「不可能」と判定する。
実装は 1 例ずつ red→green で進める。N ターンで停止。
```

実装は tdd スキル準拠(1 例ずつ。テストコードの一括先行生成はしない)。

## レビュー観点(質問票の注記に埋める元ネタ)

1. バグを入れたら落ちるか(ミューテーション思考)
2. 期待値は具体的で独立か
3. 境界値・異常系が業務的に妥当か
4. 振る舞いの説明がそのままテスト名になるか(HOW でなく WHAT。UI の手順になっていないか)
5. seam 経由か(実装詳細に触れていないか)
6. リスクの根拠は書いたか(高 = 業務停止・金銭/権限・新しく曖昧)
