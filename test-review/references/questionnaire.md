# ルール一覧型の質問票

grill-visual スキルの手順(JSON → render.py → serve.sh → Monitor)に従う。
提示する URL は render.py が印字する統合ページの URL(`<root>#tr-<slug>`)。
topic 名は `tr-<チケットslug>`、JSON に `"kind": "test-review"` を書く(統合ページの絞り込み用)。

## 問いの形

- 問いは**ルール一覧型**(`"type": "rules"`)。1 問に 5〜8 ルール。seam や画面ごとに問いを分ける。
- 各行は、行頭にリスク、ルール文、例の件数(タップで横長の表が開く)、右に採用トグル(既定オン)、💬(押すと行の下に 1 行欄)。末尾に「採用 n / 不採用 n / コメント n」が出る。
- 高リスクの行は例を開いた状態で出す。中・低は畳んだまま既定で採用にする(人は開かなくてよい)。抜き打ちの明示確認は入れない(ユーザー決定 2026-11-20)。

データの形:

```json
{"id": "Q1", "type": "rules", "title": "API・ログイン(5 ルール・13 例)",
 "body": "seam: HTTP の入口。高リスク 2 件は例を開いて確認してください。",
 "rules": [
   {"id": "R1", "text": "ログインなしでは API を使えない", "risk": "high",
    "ears": "When クッキーなしで API を呼ぶと、システムは 401 を返す",
    "note": "期限切れは 7 日の境界を 8 日で突く",
    "cases": [
      {"id": "R1-1", "behavior": "一覧を見られない", "input": "クッキーなし GET /api/sites",
       "expected": "401", "kind": "異常系"}
    ]}
 ]}
```

回答は `answers["Q1"] = {"R1": "adopt", "R4": "reject"}`。1 行コメントは `notes["Q1/R4"]`、問い全体のメモは `notes["Q1"]` に入る。

## 見せ方の決めごと

- ID(R1、R1-2 など)は管理用で、ユーザーに読ませない。行の文は「ユーザーは◯◯できる」の文、分類や seam は日本語名(「API・ログイン」「画面・写真タブ」)で書く。
  ユーザーの声: 「R, N などのアルファベットが分からず、それだけあまり意味をなしてない」
- 例の表は 1 例 = 1 行の横長の表(列: 振る舞い / 入力 / 期待結果 / 分類)。例ごとに縦の表を作らず、文章でも流さない。
  ユーザーの声: 「4 つが各 1 行になっていて、振る舞いが 1 列で 4 つ見れたのでパッと見やすかった」
- この表は test-review の質問票だけで使う。計画の grill や ui-check の質問票は従来どおり。
- ルールの `note` に AI 側の注記(なぜこの期待値か、どの境界を突くか、なぜこのリスクか)を書く。
- info タブにルールと例の全体、seam、チケット参照、未解決の問いを載せる。
- 全体の自由記述欄で「足りないルール、ドメイン的な違和感」を明示的に募る。ユーザーは推奨どおり選びつつ、メモ欄で本質的な指摘をする傾向がある。メモは必ず反映し、次ラウンドで確認する。

## ラウンドの回し方

「不採用」と「コメントあり」のルールだけを次ラウンドで再提示する。直した例の表は開いた状態で出す。
全採用で完了。
