# ルールと例の書き方

## ルール

1 チケットで 3〜8 件が目安(例の数の 1/3〜1/5)。

- 1 行の業務ルール。「ユーザーは◯◯できる」「◯◯のときは△△しない」の文で書く。
- **EARS 1 行**を添える: `When <きっかけ>, the <system> shall <応答>`。型は Ubiquitous / When / While / If-Then / Where の 5 つ。期待値の具体的な値は例の側に置く。
- **リスク**(高 / 中 / 低)を付ける。基準は影響 × 不確かさ。
  - 高: 壊れると業務が止まる。お金や権限に関わる。仕様が新しく曖昧。
  - 低: 既存の振る舞いの踏襲。表示だけ。外しても気づいてすぐ直せる。
- 画面に関わるルールは、どの画面かを括弧で添える。ui-check の差分確認で使う。

## 例

ルールごとに 1〜5 件。

- 列は `ID / 振る舞い / 入力 / 期待結果 / 分類`。ID は `R1-1` のようにルール番号つき。
- 分類は正常系・異常系・境界値(空、0、負数、最大長)・例外をルール全体で網羅する。指定しないとハッピーパスに偏る。
- 期待結果は具体的な値で書く。「正しく動く」「エラーにならない」は期待結果にならない。
- 期待値は独立した正解(仕様、手計算、既知の実例)から取る。実装と同じ計算式で導いた値はトートロジーになる。
- テストは合意済みの seam 経由で書く。private 関数、DB の直接参照、内部コラボレータのモックには触れない。
- 業務的に意味のある例だけを置く。数合わせの分岐網羅はしない。
- 振る舞いは「ユーザーは◯◯できる」の形で書く。テスト名にそのまま使える。UI の手順(「ボタン X を押す」)で書くと、画面が変わるたびに文言が変わる。判定は「実装や画面が変わったらこの文言は変わるか」。
