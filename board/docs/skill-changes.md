# スキルの文面の変更案: 子の報告を記録に移す

board の最初の版に合わせて、子の報告を「中心へのメッセージ」から「`flow` コマンドの記録」に移すための変更案。
この作業ではスキルのファイルを編集していない(作業ツリーが `~/.claude/skills` からリンクされ、保存した瞬間に全セッションに効くため)。
board を実物で使えると確かめてから、別のブランチで反映する。

方針(仕様「情報の流れ」より):

- 段階が変わったとき・報告したいときは、子が `flow` で記録する。中心へは送らない。
- 中心へ SendMessage で送るのは「PR 案」と「詰まった」だけにする(どちらも記録にも残す)。
- 子は `flow` を、自分の worktree の中で引数なしに近い形で呼ぶ(プロジェクトと題材は作業フォルダから決まる)。

## 前提(反映の前に決めること)

- `flow` の呼び方: `~/bin/flow`(`exec python3 <このリポジトリ>/board/flow.py "$@"` の 1 行のラッパー)を置くか。
  置かないなら、文面に `python3 <パス>/board/flow.py` を書くことになり、パスが個人の環境に依存する。

## 1. `dev-flow/parallel/parallel.sh`(子に渡す指示文)

### 1-1. `kickoff_for` の 130 行目

変更前:

```
質問票の回答を受け取ったら、報告先の中心へ「回答を受け取った（topic・ラウンド）」と 1 行送る
```

変更後:

```
段階が変わったら flow step <段階>、区切りの報告は flow report "<1 行>" で記録する（中心へは送らない）
質問票の回答を受け取ったら flow report "回答を受け取った（topic・ラウンド）" と記録する
```

### 1-2. `prompt_for` の HUB の段落(162〜168 行目)

変更前:

```
中心セッション「$HUB」が統合ブランチ・マージ・ボード・本番を持っています。
次のタイミングで SendMessage で「$HUB」宛に 3 行ほど報告してください:
質問票 (grill-visual) を出したとき (URL を必ず添える) / 質問票の回答を受け取ったとき (topic とラウンドを 1 行) /
仕様確定 / 実装 green / 詰まった /
PR の案 (タイトル・本文の全文・変更ファイル・テスト結果・frontend なら ui-check の URL)。
```

変更後:

```
中心セッション「$HUB」が統合ブランチ・マージ・ボード・本番を持っています。
進み具合は flow コマンドで記録します（中心へは送りません。board の画面に出ます）:
  段階が変わったとき … flow step 計画|仕様|チケット|テストレビュー|UI確認|実装前の説明|実装|レビュー|完了
  質問票を出したとき … flow report "計画の質問票を出した" --link 質問票=<URL>
  回答を受け取ったとき・仕様確定・実装 green … flow report "<1 行>"
  実装前の説明を出したとき … flow report "実装前の説明を出した" --link 実装前の説明=<URL>
SendMessage で「$HUB」宛に送るのは次の 2 つだけです（どちらも flow でも記録する）:
  詰まった … flow stuck "<理由>" のあと、同じ 1 行を送る
  PR の案 … 案をファイルに書き（1 行目がタイトル、残りが本文の全文）、flow pr-draft <ファイル> のあと、
            タイトル・変更ファイル・テスト結果・frontend なら ui-check の URL を送る
```

## 2. `dev-flow/parallel/README.md`

### 2-1. 「### 3. 子の報告を受ける」(66〜75 行目)

変更前の要点: 「子は次の区切りで、中心へ SendMessage で 3 行報告する」と 6 つの区切りの箇条書き。

変更後:

```
### 3. 子の進み具合を見る

子は区切りごとに `flow` で記録する。中心へは送らない。進み具合は board の画面(表)で見る。
中心へ SendMessage で届くのは「詰まった」と「PR 案」だけである。
質問票の回答の到着も記録に残るので、中心はユーザーのチャットに「回答が届いた」と書かなくてよい。
```

### 2-2. 「### 5. PR 案を検証して PR を作る」の手順 1(118 行目)

変更前:

```
1. PR 案をユーザーに提示する。OK が出たら、中心が `gh pr create` する。
```

変更後:

```
1. PR 案はユーザーが board の画面で読み、「承認」を押す。中心には「承認された」と届く。
   中心は記録の PR 案の全文で `gh pr create` する(承認の記録が無ければ作らない)。
```

決めごとの「ユーザーの承認は、ユーザー本人の回答だけ」に、「board の承認の記録(`kind: approve`)は本人の操作として扱う」を足す。

## 3. `dev-flow/SKILL.md`(手順の各ステップの「終わり」)

並列運用でないときも記録が残るように、手順 1〜8 の「終わり」の行の前に 1 文を足す案。
例(手順 1):

変更前:

```
   終わり: 深さが決まり、決めることが尽きた。
```

変更後:

```
   段階に入ったら `flow step 計画` で記録する(board の表に出る)。
   終わり: 深さが決まり、決めることが尽きた。
```

手順 2〜8 も同じ形で、`仕様` `チケット` `テストレビュー` `UI確認` `実装前の説明` `実装` `レビュー` を書く。
マージされたら `flow step 完了` を書く。

## 4. プロジェクトごとの子の定義(各プロジェクトの `.claude/agents/issue-worker.md`)

このリポジトリの外にあるので、ここでは方針だけ書く。
`parallel.sh` の 1-2 と同じ文を、agent 定義の「報告」の節に入れる。SendMessage で送る区切りを「詰まった」「PR 案」の 2 つに減らす。
