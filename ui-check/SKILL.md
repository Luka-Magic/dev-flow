# UI Check — 実装前に画面のイメージを確認する

ルールと例は「何ができるか」を固めるが、「どう見えるか」は固めない。
UI に触れる変更では、承認済みのルール・例を画面の形にしたモックを見せて、
実装に入る前にズレを潰す。**UI に触れない変更(API だけ・バッチ・雑務)では飛ばす。**

計画の grill(dev-flow ステップ 1)で画面の**構造**は選んでいる。ここで見るのは
「承認済みのルール・例を満たすには、その構造の中に何が要るか」(空の状態・エラー表示・
必須項目・操作の結果)。同じ絵を二度見せる場ではない。

## 位置

dev-flow: 計画(構造のモック)→ 仕様 → テストレビュー(承認)→ **UI 確認(差分)** → 実装 → レビュー → PR

## 手順

1. **対象の画面を決める(差分)**
   - 計画の grill で構造を承認した画面のうち、**テストレビューで仕様が変わった画面**と、
     grill では出していない画面(詳細・エラー・空状態など)だけをモックにする。
     変わったかどうかは、承認済みルールに添えた画面名(test-review 手順 2)と、
     grill の回答以降に spec を直したかで判断する
   - **どの画面も変わっていなければモックは作らず**、手順 2 の対応表の確認 1 問だけ出す
2. **モックを作る** — 置き場所を先に選ぶ。どちらでも見せ方は共通:
   **1 ページ・上部にタブ**(1 画面 = 1 タブ。名前は「写真タブ」「探鳥行の詳細」のような画面名)、
   `#<タブ名>` のハッシュで直接開け、質問票の各問はそのハッシュ付き URL にリンクする。
   画面ごとのページに分けない。スマホ幅(390px)で崩れないこと(タブは横スクロール可)。
   ユーザーの声: 「モックの表示、すごくよい。1 つの URL 内で上部にタブを入れて 1 ページから全部見たい」

   モックは段階で粗さを変える。**大枠(何が主役か・どう辿るか)は計画の grill で、粗い静的 HTML で
   決め終えている**。ここで見るのは詳細(空の状態・エラー・必須項目・操作の結果)なので、
   本物の部品で見せる A を既定にする。新規画面も A(grill で決めた構造を本物の部品で組む)。

   | 条件 | 置き場所 |
   |---|---|
   | 既定(既存画面の変更・新規画面とも) | **A. 開発サーバーの一時ルート** |
   | dev サーバーが無い・起動できない / 部品がまだ 1 つも無いプロジェクト | **B. 単体 HTML** |

   ここで構造そのものを選び直したくなったら(案を並べて比べたい)、モックを作り込まずに
   計画の grill に戻り、粗い静的 HTML の複数案で決め直す。

   **A. 開発サーバーの一時ルート**(本物の部品と CSS で見せ、「実装したら印象が違った」を防ぐ)
   - チケットの作業ブランチで、`/dev/mock/<チケットslug>` のルートを 1 つ足す。
     中身は**本物のコンポーネント + ダミーデータ**(ファイル内の固定値。API・DB を叩かない。
     API が要る部品は props で値を渡すか、プロジェクトに MSW 等があればそれを使う)
   - **開発時だけ有効にする**(`import.meta.env.DEV` / `process.env.NODE_ENV === 'development'` 等で
     ルート登録ごと分岐)。本番ビルドに含まれないことを、ビルド結果を `mock` で grep するなどして確かめる
   - 既存画面の変更なら、各タブで **before(今の本物の画面)/ after(モック)を並べる**
   - 計画の grill の静的モックは構造の見本として読む(構造は変えない。HTML は流用しない)
   - モックの追加は 1 コミットにまとめる(`chore(mock): <slug> の UI 確認用ルート`)。後で消すため
   - 質問票からのリンクは、grill の質問票と同じくユーザーの端末から開けるホスト名にする
     (dev サーバーが localhost だけで待ち受けているなら、外から開けるよう起動し直す)
   - プロジェクトに ui-comments(`.ui-comments/` と `packages/ui-comments/`)があれば、
     モックの画面上でのコメントも受け付ける。**判断の正は質問票の回答**、コメントは補足として読む

   **B. 単体 HTML** — `~/.agent/diagrams/assets/<topic>/index.html` に置く。
   静的 HTML、実データ・API 不要。プロジェクトのテーマ(CSS 変数・書体・角丸)を流用して本物に近づける。
   既存画面の変更なら各タブの中で before / after を並べる。
   配信は grill-visual と同じサーバー(`~/.agent/diagrams/` 配下がそのまま見える)。
   計画の grill で作ったモックがあれば、そのファイルを起点にしてよい(構造は変えない)。
3. **質問票を出す** — grill-visual、topic `ui-<チケットslug>`、JSON に `"kind": "ui-check"`。
   - モックにした画面は **1 画面 = 1 問**。選択肢は「このまま(推奨)/ 直す(メモに何を)/ 作り直す」。
     各問にモックへのリンク(スクリーンショットが撮れるなら `image` も)。
     `answer_note` に「この画面が満たすルールと例」を **ID ではなく文で** 書く(ID は括弧で添えるだけ)
   - 変わっていない画面は問いにせず、info タブの対応表に「計画の grill `<topic>` Q<n> で承認、変更なし」と書く
   - 全画面が変更なしなら、問いは **「承認済みルールと画面の対応表はこれでよいか」の 1 問**だけ
     (選択肢: よい(推奨)/ 足りない画面がある(メモに))
   - info タブに承認済みルール・例との対応表。全体自由記述欄で「足りない画面・操作」を募る。
     並列運用なら render.py が印字する統合ページ URL(`<root>#ui-<slug>`)を中心セッションへ送る
4. **回答を反映する**
   - 全部「このまま」→ A なら一時ルートを消す(`chore(mock)` のコミットを `git revert`)→ 実装へ
   - 「直す」がある → 仕様(`docs/specs/`)を直す → 影響する**ルール・例だけ** test-review で再提示 →
     再承認後に `docs/test-cases/` を書き換える(承認前に書き換えない)→ モックを直して**その画面だけ**再提示。
     両方が採用になるまで繰り返す
5. **実装後** — 実機の画面(dev サーバーの URL か スクリーンショット)を PR 案に添える。
   モックと違えた点があれば理由を書く。

## 決めごと

- モックは捨てる前提。**モックの HTML や一時ルートを実装に流用しない**(実装の正は仕様とルール・例。
  画面は 1 例ずつ red → green で作り直す)。一時ルートは実装に入る前に消し、PR の diff に残さない
  (PR 前に `git diff main...HEAD` で `/dev/mock` が無いことを確かめる)
- 実行するかは計画の grill で選んだ UI の深さ(`depth-ui`)で決まる。`detail` / `full` なら飛ばさない。
  `none` なら作らず、実装後のスクリーンショットを PR 案に添える。
  対応表 1 問で終える場合も質問票は出す(check-pr.sh は `answers/ui-*` の回答ファイルの有無を見る)
- 見た目の好み(色・余白)は聞かない。聞くのは配置・導線・情報の有無・操作の意味
- スクリーンショットが要るときは agent-browser か playwright(コンテナ内)。無ければリンクで足りる
