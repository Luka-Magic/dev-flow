# ui-check

ルールと例は「何ができるか」を固めるが、「どう見えるか」は固めない。
UI に触れる変更では、承認済みのルールと例を画面の形にしたモックを見せ、実装に入る前にズレを潰す。

計画の grill(dev-flow のステップ 1)で画面の**構造**は選んである。ここで見るのは「承認済みのルールと例を満たすには、その構造の中に何が要るか」(空の状態、エラー表示、必須項目、操作の結果)である。同じ絵を二度見せる場ではない。

実行するかは、計画の grill で選んだ UI の深さ(`depth-ui`)で決まる。`detail` と `full` なら実行する。`none` なら作らず、実装後のスクリーンショットを PR 案に添える。

## 用語

- **差分**: 計画の grill 以降に仕様が変わった画面と、grill では出していない画面(詳細、エラー、空の状態など)。モックにするのはこの差分だけ。
- **一時ルート**: 開発サーバーに足す `/dev/mock/<チケットslug>` のルート。本物の部品とダミーデータで画面を組む。開発時だけ有効で、承認後に消す。
- **単体 HTML**: 開発サーバーが使えないときの代替。`~/.agent/diagrams/assets/<topic>/index.html` に置く静的 HTML。

## 手順

1. **対象の画面を決める**。承認済みルールに添えた画面名(test-review の `references/rules-and-cases.md`)と、grill の回答以降に spec を直したかで、差分の画面を選ぶ。
   どの画面も変わっていなければモックは作らず、手順 3 の対応表の確認 1 問だけを出す。
2. **モックを作る**。既定は一時ルート。開発サーバーが無い、起動できない、部品がまだ 1 つも無いプロジェクトでは単体 HTML。作り方は [references/mock-route.md](references/mock-route.md)。
   どちらでも見せ方は共通で、1 ページ・上部にタブ(1 画面 = 1 タブ。名前は「写真タブ」「探鳥行の詳細」のような画面名)、`#<タブ名>` のハッシュで直接開ける。スマホ幅(390px)で崩れない(タブは横スクロール可)。
   ユーザーの声: 「モックの表示、すごくよい。1 つの URL 内で上部にタブを入れて 1 ページから全部見たい」
   構造そのものを選び直したくなったら(案を並べて比べたい)、作り込まずに計画の grill に戻り、粗い静的 HTML の複数案で決め直す。
3. **質問票を出す**。grill-visual で、topic は `ui-<チケットslug>`、JSON に `"kind": "ui-check"`。
   - モックにした画面は 1 画面 = 1 問。選択肢は「このまま(推奨)/ 直す(メモに何を)/ 作り直す」。各問にモックのハッシュ付き URL をリンクし、スクリーンショットが撮れるなら `image` も付ける。
   - `answer_note` に「この画面が満たすルールと例」を ID ではなく文で書く(ID は括弧で添える)。
   - 変わっていない画面は問いにせず、info タブの対応表に「計画の grill `<topic>` Q<n> で承認、変更なし」と書く。
   - 全画面が変更なしなら、問いは「承認済みルールと画面の対応表はこれでよいか」の 1 問だけ(選択肢: よい(推奨)/ 足りない画面がある(メモに))。対応表 1 問でも質問票は出す。`check-pr.sh` が `answers/ui-*` の回答ファイルの有無を見るためである。
   - info タブに承認済みルール・例との対応表を載せ、全体の自由記述欄で「足りない画面・操作」を募る。並列運用なら統合ページの URL(`<root>#ui-<slug>`)を中心セッションへ送る。
   終わり: 回答が届いた。
4. **回答を反映する**。
   - 全部「このまま」→ 一時ルートを消す(`chore(mock)` のコミットを `git revert`)→ 実装へ。
   - 「直す」がある → 仕様(`docs/specs/`)を直す → 影響するルールと例だけを test-review で再提示 → 再承認後に `docs/test-cases/` を書き換える(承認前には書き換えない)→ モックを直して、その画面だけ再提示する。両方が採用になるまで繰り返す。
   終わり: 全画面が「このまま」で、一時ルートが消えている。
5. **実装後**。実機の画面(dev サーバーの URL かスクリーンショット)を PR 案に添える。モックと違えた点があれば理由を書く。

## 決めごと

- モックは捨てる前提。実装の正は仕様とルール・例で、画面は 1 例ずつ red → green で作り直す。一時ルートは実装に入る前に消し、PR の diff に残さない(PR 前に `git diff main...HEAD` で `/dev/mock` が無いことを確かめる)。
- 聞くのは配置・導線・情報の有無・操作の意味。色・余白は後で決める。
- スクリーンショットが要るときは agent-browser か playwright(コンテナ内)。無ければリンクで足りる。
