# UI Check — 実装前に画面のイメージを確認する

ルールと例は「何ができるか」を固めるが、「どう見えるか」は固めない。
UI に触れる変更では、承認済みのルール・例を画面の形にしたモックを見せて、
実装に入る前にズレを潰す。**UI に触れない変更(API だけ・バッチ・雑務)では飛ばす。**

計画の grill(dev-flow ステップ 1)で画面の**構造**は選んでいる。ここで見るのは
「承認済みのルール・例を満たすには、その構造の中に何が要るか」(空の状態・エラー表示・
必須項目・操作の結果)。同じ絵を二度見せる場ではない。

## 位置

dev-flow: 計画(構造のモック)→ 仕様 → テストレビュー(承認)→ **UI 確認(差分)** → 実装 → レビュー → PR

## 手順

1. **対象の画面を決める(差分)**
   - 計画の grill で構造を承認した画面のうち、**テストレビューで仕様が変わった画面**と、
     grill では出していない画面(詳細・エラー・空状態など)だけをモックにする。
     変わったかどうかは、承認済みルールに添えた画面名(test-review 手順 2)と、
     grill の回答以降に spec を直したかで判断する
   - **どの画面も変わっていなければモックは作らず**、手順 2 の対応表の確認 1 問だけ出す
2. **モックを作る** — `~/.agent/diagrams/assets/<topic>/index.html` の **1 ページ**にまとめる。
   **上部にタブ**(1 画面 = 1 タブ。名前は「写真タブ」「探鳥行の詳細」のような画面名)を置き、
   タブを切り替えるだけで全画面が見られるようにする(`#<タブ名>` のハッシュで直接開ける。
   質問票の各問はそのハッシュ付き URL にリンクする)。画面ごとのファイルに分けない。
   静的 HTML、実データ・API 不要。プロジェクトのテーマ(CSS 変数・書体・角丸)を流用して本物に近づける。
   既存画面の変更なら各タブの中で **before / after を並べる**。スマホ幅(390px)で崩れないこと
   (タブは横スクロール可)。配信は grill-visual と同じサーバー(`~/.agent/diagrams/` 配下がそのまま見える)。
   計画の grill で作ったモックがあれば、そのファイルを起点にしてよい(構造は変えない)。
   ユーザーの声: 「モックの表示、すごくよい。1 つの URL 内で上部にタブを入れて 1 ページから全部見たい」
3. **質問票を出す** — grill-visual、topic `ui-<チケットslug>`、JSON に `"kind": "ui-check"`。
   - モックにした画面は **1 画面 = 1 問**。選択肢は「このまま(推奨)/ 直す(メモに何を)/ 作り直す」。
     各問にモックへのリンク(スクリーンショットが撮れるなら `image` も)。
     `answer_note` に「この画面が満たすルールと例」を **ID ではなく文で** 書く(ID は括弧で添えるだけ)
   - 変わっていない画面は問いにせず、info タブの対応表に「計画の grill `<topic>` Q<n> で承認、変更なし」と書く
   - 全画面が変更なしなら、問いは **「承認済みルールと画面の対応表はこれでよいか」の 1 問**だけ
     (選択肢: よい(推奨)/ 足りない画面がある(メモに))
   - info タブに承認済みルール・例との対応表。全体自由記述欄で「足りない画面・操作」を募る。
     並列運用なら render.py が印字する統合ページ URL(`<root>#ui-<slug>`)を中心セッションへ送る
4. **回答を反映する**
   - 全部「このまま」→ 実装へ
   - 「直す」がある → 仕様(`docs/specs/`)を直す → 影響する**ルール・例だけ** test-review で再提示 →
     再承認後に `docs/test-cases/` を書き換える(承認前に書き換えない)→ モックを直して**その画面だけ**再提示。
     両方が採用になるまで繰り返す
5. **実装後** — 実機の画面(dev サーバーの URL か スクリーンショット)を PR 案に添える。
   モックと違えた点があれば理由を書く。

## 決めごと

- モックは捨てる前提。**モックの HTML を実装に流用しない**(実装の正は仕様とルール・例)
- UI に触れるチケットでこのステップを飛ばさない。触れないチケットで無理に作らない。
  対応表 1 問で終える場合も質問票は出す(check-pr.sh は `answers/ui-*` の回答ファイルの有無を見る)
- 見た目の好み(色・余白)は聞かない。聞くのは配置・導線・情報の有無・操作の意味
- スクリーンショットが要るときは agent-browser か playwright(コンテナ内)。無ければリンクで足りる
